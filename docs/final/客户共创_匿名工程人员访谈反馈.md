# PathGuard 客户共创：匿名工程人员访谈反馈

## 记录性质

- 记录编号：访谈-001
- 受访者：匿名工程车辆规划/测试相关人员
- 访谈形式：非结构化补充访谈，后按统一问卷整理
- 用途：用于校准产品需求、解释框架和试点验收指标
- 证据边界：这是一例定性工程反馈，不代表所有客户的统计结论；后续仍需扩大访谈样本并用试点数据验证。

## 关键反馈

### 1. 候选路线规模与人工关注范围

算法内部可能生成几十到几百条候选轨迹，经碰撞、坡度、转弯半径和车辆外廓等硬约束筛选后，工程师真正需要看的通常是 5–30 条，人工重点复核最好控制在 Top-10 左右。

这直接支持 PathGuard 的产品切入点：系统不是替代局部规划器，而是在硬约束筛选之后，帮助工程师从剩余候选中确定“先看哪十条”。

### 2. 真实工作量集中在哪里

受访者认为主要工作量集中在三类任务：

1. 把现场情况整理成可信仿真场景，包括地图时效性、土堆/围挡变化、车辆外廓和载荷参数；
2. 对失败案例进行归因，区分感知漏检、定位偏差、规划过于激进和控制跟踪不足；
3. 反复比较仿真与实车结果，解释安全余量从仿真到现场的变化。

因此产品输出不能只有一个风险分数，还要同时给出证据来源、风险位置、关键指标和下一步复核动作。

### 3. 路线优先级的工程判断顺序

工程师首先判断路线是否违反硬约束，例如碰撞、无法转弯、爬坡能力不足或车尾扫掠风险。通过硬约束后，再比较安全余量、定位误差敏感性、急停/倒车频率、通行时间、能耗和任务效率。

受访者还特别强调路线稳定性：同一场景重复运行时，如果路线选择对轻微地图变化过于敏感，或多次运行结果不一致，交付风险会明显增加。

这支持 PathGuard 采用“模型主排序 + 几何规则交叉校验 + 稳定性/证据状态提示”的产品结构，而不是只按照路线长度排序。

### 4. 必须能够解释的风险

受访者希望系统至少回答：

- 风险发生在哪个位置；
- 最小安全距离是多少；
- 是车头、车尾还是铰接位置接近边界；
- 风险来自纵坡、横坡、附着、定位误差、地图变化还是人车混行；
- 仿真模型与实车动力学可能存在什么差异；
- 限速、增加安全距离或更换路线是否可能降低风险。

“综合风险分数较高”本身不足以支持工程决策。

### 5. Top-10 试用条件

受访者愿意继续试用的条件包括：

- Top-10 确实包含值得人工关注的路线；
- 结果覆盖碰撞、临边、定位不稳定、控制跟踪困难、仿真/实车差异等不同风险类型；
- 不把同一障碍物的近似随机扰动重复占满队列；
- 每条路线能够直接查看风险位置、关键数值和原因；
- 能够跳转到地图或视频回放；
- 试用阶段 Top-10 中约有 7–8 条确实值得人工关注，并减少日志、回放和实车测试安排时间；
- 不能经常漏掉真正严重的高风险路线。

## 对产品的直接调整

1. 风险队列增加“风险类型去重/多样性”提示，避免 Top-K 被相似路线占满；
2. 路线详情固定展示风险位置、最小净空、关键指标、证据等级和建议动作；
3. 将“路线稳定性”和“地图/实车差异”列为后续试点反馈字段；
4. 将 Top-10 评价从单一命中率扩展为：高风险捕获、风险类型覆盖、相似路线重复率和人工关注比例；
5. 访谈结论只作为需求证据，不把单个受访者意见写成普遍统计规律。
